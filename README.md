# LLM-Eval-Lab

大模型、Agent 与 RAG 评测工程学习项目。

## 项目背景

这个项目要解决的问题：团队在采购、选型和升级大模型时，不能只看厂商公布的跑分。厂商分数是在厂商自己的任务分布上测的，和团队实际要做的事不完全一样。签 API 合同之前，需要按自己的任务分布独立复测；模型升版之后，需要跑回归确认没有变差，再决定能不能换。

本项目就做这套独立评测：建一套来源可核对的评测集，用三种评分方式（规则判分、单元测试判分、模型评分加人工校准）给多个模型打分，最后给出一份能拍板的选型报告，而不是一张只有分数的排名表。

### 固定场景

下面是本项目设定的场景，不是真实客户。一个小型团队需要一个模型同时承担三类任务，比例固定：

| 任务类型 | 占比 | 说明 |
| --- | --- | --- |
| 中英文技术支持问答 | 50% | 双语场景，答案要准确、要能拒答没依据的问题 |
| 简单代码辅助 | 30% | 写小段代码和改错，用单元测试判分 |
| 专业知识问答 | 20% | 有标准答案的专业题，来源为课程教材习题与作业题 |

选型约束先定死，评测结果按这套约束下结论：

- 质量底线：技术支持类 pass@1 不低于 80%，代码任务测试通过率不低于 60%。达不到底线的模型直接淘汰。
- 可靠性：关键任务另看 pass^k（同一题跑 k 次全对才算过），只偶尔答对的模型不算可靠。
- 延迟：单次响应 P95 不超过 5 秒。
- 成本：平均单次调用成本不超过 0.02 元。
- 达标模型之间再比成本和延迟，给出为什么选 A 不选 B 的明确结论。

### 评测方法

- 评测集分开发集和最终测试集。调评分器和提示词只用开发集，最终结论只看测试集。
- 采样参数（温度等）固定并记录在每次运行结果里，保证结果可复现、可对比。
- 指标同时报 pass@1、pass@k、pass^k，三者分工不同：pass@1 看单次表现，pass@k 看多次尝试至少成一次，pass^k 看每次都成的可靠性。
- 报告给出每类题目的样本数、错误数和不确定性。两个模型差距落在不确定范围内时，不宣布谁更好。
- 评分器要先校准：规则评分、模型评分、人工判断三者对照，给一致率、混淆矩阵和具体误判案例，并把失败分成模型答错、评分器判错、题面有歧义三类。

### 最终产物

- 一份公开的选型报告：多个模型在三类任务上的质量、延迟、成本同表对比，加明确的选型结论和配置建议。
- 一套可复跑的回归套件：模型升版或提示词变更时重跑，判断能不能上线。

相关项目：[gitlab-handbook-rag](https://github.com/IMaLLinn/gitlab-handbook-rag) 是用本项目的评测方法评测的一个真实 RAG 应用（员工内部知识库问答助手）。两个项目是方法与产品的关系。
